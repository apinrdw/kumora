# deploy

Checking the stacks, the deploy script and the Workers Builds side without deploying.

- **Plan a stage without deploying.** With a profile holding Cloudflare and Infisical (runbook step 6), `bun alchemy plan --stage <stage> --no-input` from `apps/web` or `apps/dashboard` loads the stage's state and Infisical secrets and prints what a deploy would do. It changes nothing. Get a branch's Preview stage from `bun packages/deploy/src/teardown.ts stage <branch>`.
- **`alchemy profile edit` evaluates the stacks.** It runs them with alchemy's `PLACEHOLDER_STAGE` to discover auth providers, so a stack change that rejects that stage breaks profile setup with "Could not load auth providers from 'alchemy.run.ts'". `packages/deploy/tests/stack.test.ts` covers it. `--no-input` reaching "Cannot run selection without an interactive terminal" means discovery passed.
- **Workers Builds logs need the owner.** The API for build logs needs a token with Workers Builds read, which the deploy tokens lack, so ask the owner to paste the failed build's log. A failure at "Cloning repository... error occurred while updating repository submodules" is a submodule entry in the index; `node scripts/check-no-gitlinks.mts` names it.
- **Use the pinned fallow.** `pnpm exec fallow audit --base origin/staging`, not a `fallow` on `PATH`: CI's `fallow` job runs the pinned version, and an older global one missed findings it reports.
- **`fallow audit --base` can fail locally.** Pinned 3.39.0 in a T3 worktree exits 2 with "could not create a temporary worktree for base ref", with or without the sandbox. On 2026-11-14 the cause was `/tmp` out of inodes (`df -i /tmp` at 100%), filled by stale `fallow-audit-base-cache-*` dirs; `find /tmp -maxdepth 1 -name 'fallow-audit-base-cache-*' -mmin +30 -exec rm -rf {} +` cleared it and the audit ran. CI's `fallow` job runs the same audit, but only once the PR is out of draft; read its findings with `gh api repos/apinrdw/kumora/check-runs/<job id>/annotations`.
- **Red commits get no CI verdict.** A fix agent pushing red then green within a minute leaves the red run `cancelled`. Plant the defect locally instead: `git show <red>:<file> > <file>`, run the covering test, `git checkout -- <file>`.
- **The probe's hash check needs a logged-in Infisical CLI and the project ID.** The worktree has no `.infisical.yaml`, so pass `--projectId=5968b242-c07d-4498-8798-1a3a6002eb18` (project `kumora`). Without it, or unauthenticated, `infisical secrets get --plain` prints nothing and the hash comes out `e3b0c44298fc` (empty string). Previews read `staging`: `printf '%s' "$(infisical secrets get DEPLOY_PROBE_SECRET --projectId=<id> --env=staging --path=/web --plain --silent)" | sha256sum | cut -c1-12`. Print the prefix only.
- **An edited, already-applied D1 migration fails only the deploy.** `bun alchemy plan` shows the database as a plain `update`; the Workers Build then fails with `RewrittenMigrationHistoryError: Applied migration history in "__alchemy_migrations" does not match the local files`. A Preview applies a branch's migrations on its first push, so even a migration that never reached Staging can't be edited after that push: add a forward migration (spec #437's `0002_candle_trades.sql`).
