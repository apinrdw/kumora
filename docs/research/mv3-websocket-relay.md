# Capturing a page's WebSocket frames in an MV3 extension and relaying them to another origin's tab

Research for #41 (map #38). Read on 2026-11-06 from developer.chrome.com, Chromium source at `main` and at release tags, the Chrome DevTools Protocol schema, and the Public Suffix List. Each fact names the Chrome version it applies to when the source gives one. Lines marked **Inference** are reasoning from the cited facts, not something a source states. Check them in a spike.

## Verdict

Use a MAIN-world content script declared in the manifest at `document_start`. It wraps `WebSocket`, `fetch` and `XMLHttpRequest` on stockbit.com and Ajaib, and hands frames to an ISOLATED-world content script through `window.postMessage`. The isolated script forwards batches over a `runtime.connect` port to the service worker. The service worker forwards them over a second port, which the Market Live page opened with `chrome.runtime.connect(extensionId)` through `externally_connectable`. List each dashboard origin as an exact host. `*.workers.dev` would admit every Cloudflare Workers site. Batch the messages every 50 to 100 ms. Have both ends send a heartbeat more often than every 30 s, and reconnect on `onDisconnect`.

Keep `chrome.debugger` as a fallback for when the wrapper misses a socket, for example one opened inside a Web Worker. It is reliable for frames, but it shows a permanent "started debugging this browser" infobar. When the user clicks Cancel on that infobar, the session detaches.

## 1. Ways to read a page's WebSocket frames

### 1a. MAIN-world content script that wraps `WebSocket`

- **What it is.** The manifest key `content_scripts[].world` takes `"ISOLATED"` (the default) or `"MAIN"`. `MAIN` "share[s] the execution environment with the host page's JavaScript". See the [content_scripts manifest reference](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts).
- **Version.** Chrome 111 is the first version that honours `world` in `manifest.json`. Earlier versions ignored it. A Chromium contributor said so in the [chromium-extensions thread "Chrome 111: chrome.runtime is now undefined in content scripts"](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/_zKyp9XvIzY). For dynamic registration, the `world` field of `scripting.registerContentScripts` (`RegisteredContentScript.world`) is Chrome 102+. The same field in `scripting.executeScript` is Chrome 95+. `injectImmediately` is Chrome 102+, but it "is not a guarantee that injection will occur prior to page load". See the [scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting).
- **Timing.** At `run_at: "document_start"`, scripts are injected "before any other DOM is constructed or any other script is run". See [content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts). So a manifest-declared MAIN-world script can replace `window.WebSocket` before any site code captures a reference to it. Use the manifest declaration rather than `executeScript`, because `executeScript` with `injectImmediately` can still land after the page's scripts have run.
- **CSP.** "When a content script is injected into the main world, the CSP of the page applies" ([content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)). **Inference:** the browser injects the declared file itself, so the page's `script-src` does not block the injection. The wrapper's own behaviour runs under the page CSP, though. It cannot use `eval`, inline script tags, or `fetch` to hosts outside the page's `connect-src`. That is why it must hand data to the isolated world over the DOM and not call out over the network.
- **No extension APIs.** MAIN-world scripts lose `chrome.runtime` ([same thread](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/_zKyp9XvIzY)). They must talk to an ISOLATED-world script "through the shared DOM", and the documented example uses `window.postMessage` and checks `event.source === window` ([content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)).
- **Permissions and warnings.** You need host permissions or `content_scripts.matches` for the broker origins. The install warning is per site ("Read and change your data on …"), which is narrower than `debugger`'s all-sites warning. This extension is loaded unpacked and never published, so the warning text only matters for clarity.
- **Reliability limits.** These are **inference**, so verify them in the spike.
  - The wrapper sees only sockets created in frames it runs in. Add `all_frames: true` and `match_about_blank` / `match_origin_as_fallback` (Chrome 119+) if the site opens sockets in iframes.
  - A content script cannot reach a dedicated Web Worker or a SharedWorker. A socket opened there is invisible to the wrapper.
  - The page can detect the wrapper, for example through `WebSocket.toString()`, and could defend against it. Keep the wrapper transparent: subclass or proxy `WebSocket`, preserve `prototype`, `readyState` constants and `binaryType`, and listen with `addEventListener('message')` without replacing `onmessage`.
  - Binary frames arrive as `Blob` or `ArrayBuffer`, depending on the page's `binaryType`. Decode them in the page or forward them as structured-clone data. `postMessage` within one window keeps `ArrayBuffer`, but the extension port's JSON step does not (see 2c).

### 1b. `chrome.debugger` with the CDP `Network` domain

- **Events.** `Network.webSocketCreated`, `webSocketFrameReceived`, `webSocketFrameSent`, `webSocketClosed` and others. `WebSocketFrame` "represents an entire WebSocket message, not just a fragmented frame". `payloadData` is a UTF-8 string when `opcode` is 1, and base64 otherwise. See the [CDP schema `browser_protocol.json`](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json), Network domain.
- **HTTP bodies.** `Network.getResponseBody(requestId)` returns `body` and `base64Encoded`. Buffering is governed by the experimental `Network.enable` parameters `maxTotalBufferSize` and `maxResourceBufferSize` (same schema).
- **Availability.** `Network` is among the CDP domains open to extensions. You need the `"debugger"` permission. `attach`, `detach`, `sendCommand` and `getTargets` are Chrome 96+. Flat sessions arrived in Chrome 125: send to child targets, such as a page's workers, through `sessionId` instead of a separate attach. See the [debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger). **Inference:** with flat sessions and `Target.setAutoAttach`, the extension can also see sockets opened in workers, which the MAIN-world wrapper cannot.
- **Warning.** "Access the page debugger backend" and "Read and change all your data on all websites" ([permissions list](https://developer.chrome.com/docs/extensions/reference/permissions-list)).
- **Infobar.** While attached, Chrome shows "\<extension name\> started debugging this browser" with a Cancel button. Cancel detaches the session (`ExtensionDevToolsInfoBarDelegate::Accept()` returns `Cancel()`). The infobar closes automatically only 5 s after every session has gone (`kAutoCloseDelay = base::Seconds(5)`). See [`extension_dev_tools_infobar_delegate.cc`](https://github.com/chromium/chromium/blob/main/chrome/browser/extensions/api/debugger/extension_dev_tools_infobar_delegate.cc) and its [`.h`](https://github.com/chromium/chromium/blob/main/chrome/browser/extensions/api/debugger/extension_dev_tools_infobar_delegate.h), and the string `IDS_DEV_TOOLS_INFOBAR_LABEL` in [`generated_resources.grd`](https://github.com/chromium/chromium/blob/main/chrome/app/generated_resources.grd). The command-line switch `--silent-debugger-extension-api` suppresses the infobar ([`chrome_switches.h`](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_switches.h)). That needs a custom Chrome launch, which an owner-only setup could accept.
- **Detach.** `onDetach` reasons are `target_closed` and `canceled_by_user`. The docs mention the tab closing, and DevTools opening on the attached tab, as cases where the browser ends the session ([debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)). Treat a detach as a **Feed** going stale, and re-attach when the user acts.
- **Service worker.** "Active debugger sessions created using the chrome.debugger API now keep the service worker alive" (Chrome 118, [SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)).

### 1c. `webRequest`: handshake only

- `webRequest` intercepts the WebSocket handshake (`ws://`/`wss://`, Chrome 58+). It does not see messages on an open connection or its close. Response events expose headers and status but no body. `webRequestBlocking` is unavailable in MV3 except for policy-installed extensions. Since Chrome 72, the extension needs host permission for both the request URL and the initiator. See the [webRequest API](https://developer.chrome.com/docs/extensions/reference/api/webRequest).
- **Use:** none for frames. At most, it can detect that a socket opened as a cross-check.

### 1d. HTTP responses (candle history, stock code list)

- **In the page:** the same MAIN-world script wraps `fetch`, using `response.clone()` and reading the clone, and wraps `XMLHttpRequest` by listening for `load` on `responseText` or `response`. **Inference:** this has the same frame and worker limits as 1a. It has no permission cost beyond the host match.
- **Through the debugger:** `Network.responseReceived` / `loadingFinished`, then `Network.getResponseBody` (1b). The same infobar applies.
- `webRequest` cannot read response bodies (1c).

## 2. Streaming to the dashboard tab on another origin

### 2a. `externally_connectable` with `runtime.connect`

- The manifest lists `externally_connectable.matches`. The page calls `chrome.runtime.connect(extensionId)` or `sendMessage`, and the extension receives `runtime.onConnectExternal` / `onMessageExternal`. "Extensions cannot send messages to web pages." The page must open the port, and the extension then pushes over it. If `matches` is empty, no page can connect. See [messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging) and the [externally_connectable manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/externally-connectable).
- **Match patterns.** A host wildcard must be the first character and must be followed by `.`. A pattern without a port matches every port, so `http://localhost/*` covers `localhost:3001`. See [match patterns](https://developer.chrome.com/docs/extensions/develop/concepts/match-patterns).
- **eTLD wildcards are accepted in current Chrome.** Up to Chrome 106, `ExternallyConnectableInfo::FromValue` dropped any `*.<effective TLD>` pattern with the install warning `kErrorTopLevelDomainsNotAllowed`. The check is present in tag `106.0.5249.0` and gone from `107.0.5304.0` onwards, including `main`, where the only check is `URLPattern::Parse` ([`externally_connectable.cc`](https://github.com/chromium/chromium/blob/main/extensions/common/manifest_handlers/externally_connectable.cc)). The legacy MV2 docs page still describes the old rule. `workers.dev` and `pages.dev` are in the Public Suffix List's private section, under "Cloudflare, Inc." ([PSL](https://publicsuffix.org/list/public_suffix_list.dat)). So `https://*.workers.dev/*` now loads, but it would let **any** Cloudflare Workers site connect. List production, the custom domain and each preview host exactly, or use a preview-naming scheme under a domain the owner controls. Also validate the origin at runtime (next bullet).
- **Origin check at runtime.** `MessageSender.origin` (Chrome 80+) is "the origin of the page or frame that opened the connection". `url` is the iframe's URL if the sender is in an iframe. `documentId` is Chrome 106+. See the [runtime API](https://developer.chrome.com/docs/extensions/reference/api/runtime). In `onConnectExternal`, check `port.sender.origin` against an allowlist, and `disconnect()` anything else.
- **Serialization.** JSON, not structured clone. `undefined` becomes `null`, functions throw, and the maximum message size is 64 MiB ([messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging)). Binary payloads need base64 or a decoded form.
- **Content-script hop.** A content script cannot message another tab directly. `runtime.connect` from a content script reaches extension listeners ("does not connect to any listeners in a content script", [runtime API](https://developer.chrome.com/docs/extensions/reference/api/runtime)). The path is therefore broker-tab isolated script → port → service worker → `onConnectExternal` port → Market Live.

### 2b. Content-script bridge on the dashboard with `window.postMessage`

- An alternative is a content script injected into the dashboard origins, which receives from the service worker and calls `window.postMessage` to the page. This adds a hop and needs host permission for the dashboard origins. The page must also check `event.source === window` and the message shape, because any script on the page can post the same messages ([content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)). It has no advantage over 2a for a page the owner controls. 2a also gives an origin the browser verified (`sender.origin`) instead of a message shape that anything can forge.

### 2c. Throughput and latency

- No primary source gives a message-rate ceiling for extension ports. The documented costs are JSON serialization per message and IPC between processes. **Inference:** at a few hundred trades per second, send one message per trade over two process hops (broker renderer to the service worker, then the service worker to the dashboard renderer), and that serialization and IPC cost lands on every trade. Batch in the isolated script, either every 50 to 100 ms or every N trades. That gives about 10 to 20 port messages per second at a tape latency people do not notice. Benchmark it in the spike, following `pstack:benchmark-checklist`.
- Batching also keeps traffic flowing, and that traffic is what keeps the service worker alive (section 3).

## 3. Service worker lifetime for a long-lived relay

From the [service worker lifecycle docs](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) and the [Chrome 110 blog post](https://developer.chrome.com/blog/longer-esw-lifetimes):

- The service worker terminates after 30 s with no activity. Receiving an event or calling an extension API resets the timer (Chrome 110+). It is also stopped if one event or API call takes more than 5 minutes, or a `fetch()` response takes more than 30 s to arrive. Chrome 110 removed the hard five-minute maximum lifetime.
- **Ports.** Chrome 114+: "Sending a message with long-lived messaging keeps the service worker alive", and "Opening a port no longer resets the timers". So an idle open port does **not** keep the worker alive. Messages do. During quiet periods (pre-open, lunch break, after close), both the broker-tab script and Market Live must heartbeat more often than every 30 s, for example every 20 s.
- **Other keepalives.** An active WebSocket held by the service worker extends its lifetime, and each message resets the idle timer (Chrome 116). A debugger session keeps the worker alive (Chrome 118). So does `connectNative` (Chrome 105). Messages from an offscreen document reset the timers (Chrome 109). The minimum alarm period is 30 s (Chrome 120).
- **Offscreen documents** (Chrome 109+). Only one is open per profile at a time, and only the `runtime` API is available there. Only `AUDIO_PLAYBACK` has an automatic close (30 s without audio). Other reasons, such as `WORKERS`, `BLOBS` or `DOM_PARSER`, stay open until closed. `runtime.getContexts()` (Chrome 116+) detects an open one. See the [offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen). The docs do not say that an open offscreen document keeps the service worker alive. **Inference:** it could serve as a non-sleeping hub for merging both feeds, but this relay does not need one. Merging and deduplication belong in the dashboard, and the service worker only forwards.
- **Recovery.** `onDisconnect` fires when the other end goes away ([messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging)). When the service worker stops, both ports drop. **Inference:** each end should reconnect on `onDisconnect`. Market Live calls `chrome.runtime.connect` again, which revives the worker. The broker script reconnects and re-sends a snapshot. The dashboard shows the gap as **Freshness**.

## Open questions for the spike

1. Does Stockbit or Ajaib open its running-trade socket in the main thread, in an iframe, or in a worker? This decides whether 1a is enough or 1b is needed.
2. What is the frame encoding (text JSON, binary protobuf or msgpack), and how is it decoded?
3. What port throughput can a batched relay sustain at measured peak rates?
4. Do the preview hostnames fall under a pattern narrower than `*.workers.dev`? If they don't, the manifest needs a regenerated list, or a runtime allowlist behind a broad pattern.
