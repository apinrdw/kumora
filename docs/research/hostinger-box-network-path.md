# How the relay's ingest socket and the Worker's reads reach the Hostinger box

Research for apinrdw/kumora#537 (map apinrdw/kumora#534). Sources are Cloudflare's docs and changelog, Hostinger's support pages, DuckDB's Quack docs, Caddy's docs and the vendored Alchemy source, read 2026-11-18. The box is the owner's Hostinger KVM 2 (2 vCPU, 8 GB). Every stage ingests on it, each into its own DuckDB database. There is no standby. The Cloudflare account already holds the `pusat.ai` zone (`apps/dashboard/alchemy.run.ts`). Stages serve on `*.kumora.workers.dev` (`packages/deploy/src/target.ts`).

## Short answer

Use one Cloudflare Tunnel from the box for both paths, and open no inbound port on it.

- **(a) Relay ingest socket.** Publish one hostname on the tunnel, for example `ingest.pusat.ai`, mapped to the box service on `localhost`. Cloudflare Tunnel has "full support for Websockets" ([Tunnel FAQ][tunnel-faq]), it is free up to 1,000 tunnels per account ([Tunnels for Platforms][tfp]), and `cloudflared` makes only outbound connections ([Tunnel overview][tunnel]). The box's IP stays out of DNS, so Hostinger's null routing ([Anti-DDoS events][hst-ddos]) is much less likely to take it off the network. Put the stage in the URL path, not in the hostname, and give each stage its own ingest token.
- **(b) The Worker's reads.** Bind the dashboard Worker to the same tunnel with a Workers VPC Service (HTTP) aimed at the box service on `localhost`. Reads then have no public route at all. Workers VPC is in beta and free on all Workers plans while it is in beta ([Workers VPC][vpc]). Alchemy already has a `Cloudflare.VpcService.VpcService` resource (`repos/alchemy/packages/cloudflare/src/VpcService/VpcService.ts`). If the beta fails, the fallback is the public tunnel hostname with a bearer token.
- **Don't route the relay through a Worker.** That path keeps the relay's target URL unchanged, but it adds a hop and a second failure surface: Worker runtime updates close sockets after a 20-minute grace period ([Workers limits][wlimits]). It saves nothing that Tunnel doesn't already give.
- **A public Caddy endpoint is the fallback.** It works and has the fewest Cloudflare dependencies. But it publishes the box's IP and needs ports 80 and 443 open to the internet ([Caddy automatic HTTPS][caddy-https]). It also leaves DDoS handling to Hostinger, whose firewall "isn't intended to block" DDoS volumes ([Hostinger firewall][hst-fw]).

## Recommended layout

Not built or measured; this is a reading of the sources above.

1. **One tunnel, owned outside the stage stacks.** Create it once, by hand or from a separate box stack. Run `cloudflared` as a system service on the box. Turn its auto-update off and update it in a closed-market hour, because an update restarts `cloudflared` ([run parameters][run-params]) and drops every socket.
2. **One published hostname for the relay**, for example `ingest.pusat.ai` → `http://localhost:<port>`, with the stage in the path (`/ingest/<stage>`). The box service maps the stage to its DuckDB file and checks that stage's ingest token in the first envelope, as the trading-day object does today (`packages/relay/GLOSSARY.md`). Cloudflare Access service tokens can't gate this socket, because a WebSocket opened from the relay's service worker can't set custom request headers (inference from the WebSocket API).
3. **One VPC Service per read endpoint on the dashboard Worker**, pointing at the box service through the tunnel. The Worker passes its stage in the path and a per-stage token. Preview teardown asks the box to drop that stage's database over the same binding.
4. **Relay change.** Today the relay derives its ingest URL from the dashboard origin (`apps/extension/src/worker/target.ts`, `ingestUrl`). A target needs a separate ingest URL. The manifest's `Decision:` comment says the extra target's ingest socket "needs no host permission" (`apps/extension/manifest.ts`), so a new host shouldn't need a manifest change.

## Open points the docs don't settle

- **Which Cloudflare data centers serve each end.** Cloudflare doesn't say which data center an Indonesian ISP's traffic reaches. Measure it: `colo=` in `https://pusat.ai/cdn-cgi/trace` from the owner's machine and from the box, and the connector locations in `cloudflared tunnel info`. If either end lands in Singapore, compare the round trip with a direct `wss://` to the box before you choose.
- **Hostinger's Indonesia city.** Hostinger's pages list Indonesia, not a city ([Hostinger locations][hst-loc]). The access ticket records the box's region. A VPS location "is fixed after initial setup".
- **Cloudflare's WebSocket idle timeout value.** The docs give no number. The connection limits page lists a 125 s Proxy Read Timeout and a 900 s Proxy Idle Timeout, and doesn't mention WebSockets ([connection limits][conn-limits]). The relay's traffic makes this moot in hours. A viewer socket during lunch break would depend on its own heartbeat.
- **WebSocket upgrades over a Workers VPC binding.** No VPC page or changelog entry mentions WebSockets ([VPC API][vpc-api]; [VPC changelog][vpc-log]). It matters only if a Durable Object or Worker must hold a socket to the box, for example to feed viewer sockets that stay on a Durable Object. A test with a VPC Service and a small WebSocket echo server would settle it.
- **Workers VPC beta.** "Features and APIs may change before general availability" ([Workers VPC][vpc]). No GA date or post-beta price is published.
- **The Worker can't speak Quack directly.** Quack runs over HTTP or HTTPS on port 9494, and DuckDB recommends "binding the server to localhost and fronting it with a TLS-terminating reverse proxy" ([Quack overview][quack]). Its messages use DuckDB's binary serialization, and the docs name no JavaScript client. Inference: the Worker reads through an HTTP API on the box service, not through Quack, and Quack stays on `localhost` for the owner's own analytics. The reads ticket decides this.
- **Null routing and the tunnel.** A null route blocks "all incoming traffic to the affected IP address" ([Anti-DDoS events][hst-ddos]). Inference: that would also cut the tunnel's outbound connections, because their replies come back to the same IP. With the IP unpublished, an attack is less likely, but nothing prevents one.
