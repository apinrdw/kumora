# ArchiveDb is the source of truth for runs

Each archive's runs lived in its R2 bucket as one JSON record per run and a latest pointer, so the admin pages listed and read R2 across an ocean for every load (apinrdw/kumora#659). Every run of either archive is now a row in ArchiveDb's `run` table (`archive-migrations/0002_runs.sql`), keyed by archive, run kind and id, with the columns its reads filter and sort on and the whole record as JSON. A run's steps rewrite only its row, and a read decodes the record with today's run schemas, so an old record still decodes as ADR 0052 keeps it. A record can be as large as a run's summary step returns, 1 MiB, so a read of many runs cuts each record to the fields it shows in ArchiveDb (`json_object` over `->`, which keeps each field's JSON type) and never reads whole records of more than a few runs: 30 days of hourly runs would otherwise hold 720 MiB, past a Worker's 128. The R2 records and pointers are frozen: nothing writes them again. Each run kind imports them once, from the first time it is read or claimed on a stage, and `run_import` marks it imported so no later read touches R2. A Worker invocation may make 1,000 D1 queries, a batch each, and 10,000 subrequests, every D1 and R2 call, so one invocation's import of a kind writes at most `IMPORT_BATCHES`, 20 batches of 10 records: at most 22 D1 queries and about 250 subrequests a kind, whatever R2 holds. Every record it reads leaves a mark, its run's row or a row in `run_import_passed`, and `run_import_found` marks each reader past retention that has found its run (`archive-migrations/0003_run_import_progress.sql`). The next invocation reads those marks and resumes, reading no record twice. Until the import finishes, a page read or a start fails with `RunsImporting`: an admin page answers a Conflict that says the history is still being copied, a start claims nothing, and a cron firing skips its run. A kind's R2 holds a few runs a day, so its import finishes on its first load. The import copies the run the pointer names, the runs of the past 30 days, and the newest run each reader older than that still finds. The e2e seeds (`apps/e2e/support/runs.ts`) write rows and mark the kind imported, as a stage past the cutover is. Undoing this means writing runs back to R2, since a stage past its import has rows R2 never saw.
